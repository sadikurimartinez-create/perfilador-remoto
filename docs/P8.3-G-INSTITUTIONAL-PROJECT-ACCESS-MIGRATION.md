# P8.3-G — Ejecución administrativa de autoridad institucional

## Propósito y frontera

Preparar la creación de `public.institutional_project_access`, autoridad PostgreSQL de acciones explícitas por proyecto. Este procedimiento **no se ejecutó live en P8.3-G**. Cada ejecución UP o DOWN requiere autorización humana separada, ambiente/base identificados y responsable administrativo. Estar listo en repositorio no acredita migración aplicada, grants aprovisionados, login real ni Rules activadas.

Rigen Manual de Gobernanza Algorítmica v2.0 → ADR-000 → ADR específicos vigentes → certificaciones/contratos recientes. ADR-016/auth hardening gobierna identidad PostgreSQL; ADR-019.19 la integridad de auditoría; ADR-011 preserva evidencia; P8.2-I/J y PRE-P8.3 fijan EXPLICIT_ACTION_GRANT_V1. Las certificaciones históricas de RBAC o control total de SUPER_ADMIN no autorizan bypass frente al contrato vigente más restrictivo. ADR-010 es soft governance analítica: no elimina controles de acceso o integridad.

## Precondiciones obligatorias

- Autorización de ejecución live, ticket/aprobación, responsable, ventana, respaldo recuperable y destino Preview confirmado por canal seguro. No deducir destino desde nombres de variables.
- `psql` disponible; sesión administrativa independiente de `ceipol_app`, con capacidad CREATE en public, propiedad administrativa de la tabla y permisos para REVOKE/GRANT. No usar el runtime ni hacerlo propietario; no concederle superuser, createrole, createdb, bypassrls o pertenencia a roles con escritura/DDL.
- El rol `ceipol_app` ya existe y dispone de USAGE en public. Su rol y todos los roles alcanzables deben carecer de CREATE en public/base, ownership y escritura en esta tabla. Revisar privilegios por columna y capacidades indirectas, incluidas funciones SECURITY DEFINER que pudieran conceder acceso de escritura. Cualquier incertidumbre impide PASS.
- El UP no crea roles y sólo concede SELECT si `ceipol_app` existe. Ausencia del rol es **BLOCKED**; no ejecutar UP suponiendo que su rama condicional lo creará.
- La tabla e índice deben estar ausentes para la primera aplicación. Si existen, detenerse y auditar su definición/estado: no ejecutar UP otra vez, no borrar datos ni declarar éxito por existencia solamente.
- Usar el canal institucional seguro para cargar la conexión administrativa en `$env:DATABASE_URL`. **No imprimir DATABASE_URL**, no usar `Get-ChildItem Env:`, transcript, command tracing, ejemplos con secretos, shell history exportado, Vercel env pull ni archivos de credenciales en el repositorio. El argumento de conexión puede ser visible a inspección local de procesos: ejecutar sólo en una estación administrativa controlada. No adjuntar líneas de proceso ni salida que contenga credenciales. El log de evidencia recoge resultados SQL sanitizados, no la conexión.
- Mantener Firebase Rules restrictivas sin activar hasta completar los gates definidos abajo. La migración vacía no crea autorizaciones ni asegura continuidad de expedientes sin grants.

## Preflight read-only

Desde la raíz del repositorio y **sólo después de autorización live**:

```powershell
psql $env:DATABASE_URL -X -v ON_ERROR_STOP=1 -f database/migrations/institutional-project-access/001_project_access_verify.sql
if ($LASTEXITCODE -ne 0) { throw 'PROJECT_ACCESS_PREFLIGHT_FAILED' }
```

`-X` evita comandos inesperados de psqlrc. El archivo sólo ejecuta SELECT de catálogo: base/roles, existencia, columnas/defaults, constraints, índice, ACL de tabla/columnas y privilegios efectivos/membresías. Funciona si faltan tabla o rol; ausencia produce NULL/filas vacías, **no PASS**. No consulta users, evidencia, Firestore ni credenciales.

Antes del UP, registrar base/rol aprobados, tabla ausente y fila runtime existente, flags privilegiados false, schema_usage true, schema_create/database_create false. Los campos de tabla todavía NULL son esperados sólo antes del UP. El owner administrativo debe ser distinto del runtime. La membresía se evalúa conservadoramente aunque NOINHERIT o SET ROLE esté limitado; no aceptar roles de escritura por inferencia. Si PUBLIC CREATE en public permite DDL al runtime, detenerse y solicitar remediación administrativa separada; este UP no modifica el esquema global ni otras tablas.

## Aplicación UP

```powershell
psql $env:DATABASE_URL -X -v ON_ERROR_STOP=1 -f database/migrations/institutional-project-access/001_project_access_up.sql
if ($LASTEXITCODE -ne 0) { throw 'PROJECT_ACCESS_UP_FAILED' }
```

El UP ya existente se conserva. BEGIN/COMMIT agrupa tabla, checks, PK, índice parcial, REVOKE PUBLIC, REVOKE runtime y GRANT SELECT. No inserta grants, no altera users y no deriva autorización de createdBy de Firestore. Un error aborta la transacción; no reintentar a ciegas tras un resultado incierto: inspeccionar catálogo y ticket antes de decidir. No usar `--single-transaction` sobre un archivo que ya administra su transacción.

## Postchecks y evidencia de PASS SQL

Repetir el comando verify anterior y evaluar **todos** los resultados:

1. Base/rol corresponden a destino y administrador aprobados; tabla ordinaria public.institutional_project_access existe con owner administrativo independiente.
2. Ocho columnas: project_id text, institutional_user_id text, relation text, allowed_actions text[], created_at timestamptz, created_by text, revoked_at timestamptz, revoked_by text. Seis primeras NOT NULL; default ASSIGNED y CURRENT_TIMESTAMP donde corresponde.
3. PK `(project_id, institutional_user_id)`; IDs/creator no vacíos; project_id normalizado; relation sólo ASSIGNED; array no vacío/sin NULL y subconjunto exacto READ, WRITE, ANALYZE_SCINCE, GENERATE_REPORT; revocación actor/fecha coherentes y fecha >= creación. Todos los constraints convalidated true.
4. Índice `idx_institutional_project_access_active_user` sobre `(institutional_user_id, project_id)` con predicate `revoked_at IS NULL`, indisvalid/indisready true; PK index válido.
5. ACL: **ninguna fila PUBLIC**, ceipol_app sólo SELECT y sin grant option; owner con privilegios propios administrativos es esperado. Ningún grant inesperado a terceros; ninguna ACL de columna que conceda derechos adicionales. Revisar la salida completa, no sólo un booleano.
6. Runtime: can_select true; can_insert/update/delete/truncate/reference/trigger false; inherits_owner false; todos sus roles alcanzables sin ownership, privilegios elevados, DDL ni escritura. No ocultar privilegios heredados detrás del REVOKE directo. No remediar roles live durante esta fase del repositorio.
7. Sólo tras demostrar que existe la tabla, comprobar filas:

```powershell
psql $env:DATABASE_URL -X -v ON_ERROR_STOP=1 -c 'SELECT count(*) AS assignment_rows FROM public.institutional_project_access;'
if ($LASTEXITCODE -ne 0) { throw 'PROJECT_ACCESS_COUNT_FAILED' }
```

En la primera aplicación sin otro administrador concurrente, se espera 0. Un resultado distinto exige investigar antes de continuar; no borrar las filas. El verify deliberadamente no referencia datos de una tabla ausente para evitar fallos de preflight. No inferir cantidad cero de NULL.

Conservar: aprobación, fecha UTC, operador, ambiente/base/rol sanitizados, commit y hashes SQL, exit codes y resultados de pre/postchecks, conteo y health-check Preview. No conservar conexión, tokens, contraseñas, perfiles personales o contenido de expedientes. Un health-check positivo comprueba existencia/SELECT/PostGIS; no sustituye constraints ni auditoría completa de ACL.

## Rollback destructivo separado

**Únicamente si la tabla sigue completamente vacía**, sin grants activos **ni revocados/históricos** y con aprobación explícita de rollback. Respaldar evidencia de catálogo/ACL. El conteo previo orienta al operador; la comprobación decisiva ocurre bajo ACCESS EXCLUSIVE dentro del DOWN. Coordinar la ventana y cancelar/abortar ante espera de lock excesiva; nunca matar procesos ajenos automáticamente.

```powershell
psql $env:DATABASE_URL -X -v ON_ERROR_STOP=1 -f database/migrations/institutional-project-access/001_project_access_down.sql
if ($LASTEXITCODE -ne 0) { throw 'PROJECT_ACCESS_DOWN_REFUSED_OR_FAILED' }
```

DOWN: BEGIN → rechazar runtime/tabla ausente/objeto inesperado → lock exclusivo → EXISTS sin filtro de revocación → DROP TABLE RESTRICT → COMMIT. El índice propio cae con la tabla. NONEMPTY rechaza cualquier fila; dependencias externas también impiden DROP. No hay CASCADE, DELETE, truncado, exportación implícita ni borrado de users/expedientes/informes/evidencia. Si falla, la sesión psql se cierra con transacción abortada: los datos/tabla permanecen. No resolver el error vaciando la tabla.

Post-DOWN repetir verify: tabla ausente, constraints/índices/ACL de esa tabla ausentes. El health-check de autoridad debe volver a error y los accesos continuar fail-closed. **No es una estrategia de rollback viable después de aprovisionar filas**; requiere entonces una decisión institucional distinta fuera de este procedimiento.

## Secuencia de activación posterior

Migración SQL → health-check Preview → autoridad SQL PASS → login institucional controlado → proyección PostgreSQL→Firebase → grants explícitos → validación → Firebase Rules → E2E real.

El primer login puede proyectar un conjunto vacío, nunca fabricar grants. Después del aprovisionamiento administrativo explícito y auditable se debe **refrescar nuevamente la proyección** y validar asignación/acciones/revocación/lease, USER y ADMIN/SUPER_ADMIN sin bypass, creación reservada y compatibilidad de expedientes. El aprovisionamiento conserva aprobación, actor y auditoría; runtime sólo SELECT y nunca invoca el provisioner. No aprobar Rules por tabla vacía o health-check aislado. No crear expedientes reales antes del grant WRITE vigente para su ID reservado.

Cada paso live requiere su autorización institucional correspondiente. P8.3-G no ejecuta esta secuencia, ni implementa un escritor administrativo nuevo. Las pruebas locales usan PostgreSQL WASM en memoria; no certifican PostGIS, proveedor, versión live, membresías reales ni ejecución en Preview.
