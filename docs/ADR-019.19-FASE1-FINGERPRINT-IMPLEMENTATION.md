# ADR-019.19 FASE 1 — EVENT FINGERPRINT & IDEMPOTENCY CORE

## Estado de Fase
- **Fase**: Fase 1 (Event Fingerprint & Idempotency Core)
- **Estado**: Implementado y Verificado (NO Certificado formalmente aún)
- **Fecha**: Agosto 2026

---

## Objetivo Arquitectónico
Eliminar la duplicidad de eventos en el ledger de auditoría forense (`geoint_event_logs`) mediante un núcleo de idempotencia basado en huellas digitales deterministas (SHA-256) y persistencia de control en `geoint_event_fingerprints/{fingerprint}`.

---

## Archivos Creados y Modificados

1. **`src/types/geointEventFingerprint.ts`** (Nuevo)
   - Definición de la interfaz `EventFingerprintRecord`:
     - `fingerprint`: string (SHA-256)
     - `eventId`: string
     - `expedienteId`: string
     - `traceabilityId`: string
     - `eventType`: string
     - `entityId`: string
     - `status`: string
     - `createdAt`: string

2. **`src/services/geoint/geointEventFingerprintService.ts`** (Nuevo)
   - Implementación de `generateEventFingerprint()`: Recibe `{ expedienteId, traceabilityId, eventType, entityId }` y retorna hash SHA-256 determinístico.
   - Implementación de `checkExistingFingerprint()` y `registerFingerprint()` para la colección Firestore `geoint_event_fingerprints/{fingerprint}`.

3. **`src/services/geoint/geointEventLogService.ts`** (Modificado)
   - Actualización del flujo en `createAndPersistEvent()`:
     1. Calcula el fingerprint determinístico.
     2. Verifica si ya existe en `geoint_event_fingerprints`.
     3. Si existe, recupera y retorna el evento existente de `geoint_event_logs`.
     4. Si no existe, persiste el nuevo evento y registra el fingerprint.

4. **`tests/testADR01919Fingerprint.test.ts`** (Nuevo)
   - Suite de pruebas automatizadas que cubre los 4 casos requeridos:
     - **CASO 1**: Mismo evento enviado dos veces -> 1 solo registro.
     - **CASO 2**: Dos eventos diferentes -> 2 registros.
     - **CASO 3**: Mismo expediente pero diferente traceabilityId -> eventos independientes.
     - **CASO 4**: Concurrencia simulada -> una única creación.

---

## Pruebas Ejecutadas
Las pruebas se han integrado en el orquestrador general (`tests/run.ts`) validando la correcta deduplicación y el comportamiento idempotente ante llamadas concurrentes y repetidas.

---

## Riesgos Pendientes
1. **Outbox Pattern**: No implementado en Fase 1 (pendiente para Fases posteriores). Ante caídas de red absolutas durante la escritura inicial a Firestore, la transacción local requiere reintentos offline.
2. **Atomicidad Transaccional**: La verificación de fingerprint y la persistencia del evento se realizan en dos pasos consecutivos (pre-check + write). Se recomienda transaccionar con `runTransaction` o `writeBatch` en fases avanzadas de endurecimiento.
