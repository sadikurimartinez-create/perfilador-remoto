## B. Contexto

El expediente contextual identifica el caso en el que se solicita el análisis.
El catálogo MASTER conserva identidades de pandillas independientes de ese caso.
Cada pandilla mantiene su proyecto custodio y sus grants institucionales vigentes.
La selección de una pandilla para análisis no cambia su custodia, no la asocia
persistentemente al expediente y no concede acceso a otras fuentes del custodio.

La ejecución analítica calcula y devuelve un resultado contextual. La generación,
incorporación, certificación y publicación documental son operaciones diferentes,
con sus propios permisos y gates. Un campo de respuesta denominado `report` no
convierte la narrativa analítica en documento institucional publicado.

## C. Decisión institucional

La ejecución de análisis GIS mediante IA requiere **WRITE sobre el expediente
contextual autorizado y READ sobre cada pandilla MASTER seleccionada y su
custodia accesible**. Ambas condiciones deben acreditarse en servidor antes
de invocar el modelo. WRITE contextual no sustituye READ de las fuentes.

READ se resuelve por las fronteras institucionales existentes y el proyecto
custodio real de cada pandilla; no se crea un grant MASTER paralelo. Se permite
seleccionar pandillas con custodios diferentes cuando todas las lecturas están
autorizadas. No se exige que sus custodios coincidan con el expediente contextual.

- `ANALYZE_SCINCE` continúa independiente y no se deriva de WRITE ni READ.
- `GENERATE_REPORT` continúa independiente y no se deriva del análisis GIS.
- No existe bypass por USER, ADMIN o SUPER_ADMIN.
- Proximidad territorial, nombre, `createdBy`, sesión cliente o visibilidad de un
  mapa no conceden permisos ni prueban pertenencia.
- No se crean permisos, roles o acciones; permanecen READ, WRITE, ANALYZE_SCINCE
  y GENERATE_REPORT. No se modifican grants existentes.

Esta decisión formaliza exclusivamente el uso de WRITE para esta ejecución GIS;
no modifica el significado de WRITE en otros módulos ni autoriza MASTER WRITE.

## D. Contrato de entrada por selecciones

Ruta objetivo existente: `POST /api/pandillas/analyze-gis`.
Contrato mínimo de selección:

```json
{
  "projectId": "context-project-fixture",
  "selectedGangIds": ["gang-fixture"],
  "activeLayers": ["domiciles", "influence_zones"],
  "geometryRefs": [
    { "gangId": "gang-fixture", "geometryId": "shape-fixture" }
  ]
}
```

Los identificadores del ejemplo son ficticios. `projectId` procede explícitamente
de `uiScope.caseProjectId`; es una solicitud de contexto que el servidor debe
autorizar, nunca una afirmación de acceso. Si proyecto del componente y contexto
activo discrepan, se bloquea la solicitud. Sin contexto explícito no se ejecuta IA.

`selectedGangIds` contiene IDs persistidos únicos, no nombres o alias.
`activeLayers` sólo admite las capas ya implementadas: `domiciles`,
`influence_zones`, `corridors`, `graffiti` e `history`; su selección no añade
fuentes ni permisos. `geometryRefs` referencia geometrías persistidas dentro
de pandillas seleccionadas; puede ser vacío si no se solicitan trazos.

El cliente no enviará inventarios autoritativos: `allGangs`, domicilios, zonas,
relaciones, geometrías completas ni telemetría que afirme adquisición de fuentes.
Esos campos deben rechazarse en el nuevo contrato, no admitirse como contexto.
Los nombres y etiquetas se obtienen de la lectura institucional autorizada.

La protección contra versiones inconsistentes es obligatoria. Estos cuatro
campos no prueban por sí solos igualdad con el snapshot mostrado al usuario.
Antes de certificar la implementación deberá concretarse su precondición de
versión usando versiones documentales existentes; cualquier metadata de
concurrencia será una precondición, nunca contenido autoritativo del cliente.
No se declara esa protección implementada mediante este ejemplo mínimo.

## E. Reconstrucción institucional en servidor

1. Validar origen de solicitud, estructura de entrada y sesión institucional
   activa desde `ceipol_session`, sin confiar en roles declarados por el cliente.
2. Reutilizar `authorizeInstitutionalProjectAccess` con WRITE para el proyecto
   contextual; comprobar asignación, revocación y estado institucional.
3. Leer el catálogo MASTER mediante `InstitutionalPandillasRepository` y la
   lectura institucional existente, sin introducir un repositorio paralelo.
4. Resolver exactamente una pandilla persistida por identificador solicitado.
5. Verificar READ vigente y custodia real accesible de cada fuente, conservando
   la separación MASTER/custodia de ADR-027.1.
6. Validar que cada referencia geométrica existe dentro de la pandilla indicada,
   pertenece a la selección autorizada y conserva versión/procedencia compatible.
7. Reconstruir domicilios y zonas con `GangGISAnalysisLayer.processGISData` y los
   motores GIS existentes, sin cambiar algoritmos, coordenadas fuente, relaciones
   ni geometrías históricas. Limitar el contexto a fuentes seleccionadas.
8. Invocar IA únicamente después de completar todos los gates. Mantener
   `report`, `structuredOutput` e `isAiGenerated` en la respuesta exitosa y los
   controles vigentes de incorporación documental.

No derivar IDs persistentes a partir de nombres, posiciones o proximidad. Si el
motor existente no puede distinguir nombres repetidos, rechazar la ambigüedad
antes de IA; no fusionar entidades ni renombrarlas silenciosamente.

## F. Rechazos obligatorios

Bloquear sesión ausente o caducada; proyecto no autorizado; WRITE contextual
insuficiente; READ insuficiente sobre cualquier fuente; grants revocados;
proyecto contextual o custodio archivado o eliminado; identificadores inexistentes,
duplicados o ambiguos; referencias geométricas cruzadas o inexistentes; datos
institucionales no autorizados; payload manipulado; borradores no persistidos
presentados como evidencia; y versiones o snapshots inconsistentes.

Ante un rechazo no invocar el modelo IA, no ejecutar análisis parcial y no
reemplazar fuentes por datos del cliente. Fallar cerrado ante indisponibilidad
de autorización, lectura o comprobación de integridad. Los errores al cliente
no revelan secretos ni contenido de proyectos inaccesibles.

## G. Separación de operaciones

La autorización de ejecución GIS no concede automáticamente modificación de
registros MASTER, persistencia de resultados, publicación institucional,
generación documental ni consulta SCINCE protegida. Cada operación conserva
su frontera, autorización y controles propios. No guardar borradores para
sortear un rechazo ni incorporar automáticamente resultados a expedientes.

## H. Auditoría y trazabilidad

La futura implementación deberá registrar, mediante los mecanismos
institucionales existentes, identidad institucional del actor, proyecto
contextual, identificadores de pandillas seleccionadas, custodios y versiones
de fuentes, decisión de autorización, fecha y resultado del análisis,
referencias de evidencia utilizadas y errores/rechazos sanitizados.

Conservar la correlación entre solicitud, decisión y resultado, diferenciando
fuentes observadas, derivaciones GIS y síntesis IA. No registrar cookies,
tokens, claves, contraseñas, cadenas de conexión ni inventarios personales
completos. Un rechazo temprano registra únicamente lo disponible y verificado;
no fabrica identidad ni referencias. Si no se puede acreditar la trazabilidad
obligatoria, no declarar la ejecución certificada.

Este ADR no crea colección, esquema ni escritor de auditoría y no realiza
persistencia. La adecuación del mecanismo existente debe comprobarse en la
implementación posterior.

## I. Compatibilidad

Preservar expedientes vivos, identidades MASTER, custodias, geometrías históricas,
relaciones, versiones documentales, autorizaciones y contratos documentales.
No migrar datos, cambiar owners, Rules, roles o grants; no modificar R4 ni
asociaciones fotográficas. Los borradores permanecen locales y excluidos del
análisis institucional hasta persistencia por su flujo autorizado separado.

La sustitución del contrato de entrada exige coordinación entre UI y handler;
no habilitar un fallback que acepte inventarios cliente antiguos. Detectar y
explicar incompatibilidades de snapshot sin sobrescribir registros históricos.

## J. Certificación pendiente

Pruebas mínimas con fixtures y proveedores simulados:

- Sesión ausente/caducada; READ sin WRITE contextual; WRITE sin READ de fuente;
  proyecto ajeno; revocación; proyecto contextual/custodio archivado o eliminado;
  y ausencia de bypass para roles administrativos.
- Acceso autorizado con pandillas de custodios diferentes; reconstrucción desde
  lecturas canónicas y conservación de IDs, versiones, geometrías y relaciones.
- ID desconocido/duplicado/ambiguo; geometría cruzada/inexistente; borrador sin
  guardar; payload artificial; proyecto del componente/contexto discrepantes;
  cambio de versión o snapshot; y fallo de lectura/autorización.
- En todos los rechazos, comprobar cero invocaciones IA y ausencia de escrituras
  de datos analíticos; distinguir el registro de auditoría gobernado.
- Verificar límites de contexto, trazabilidad, respuesta exitosa compatible y
  ausencia de incorporación/publicación automática o acceso SCINCE implícito.
- Ejecutar regresiones GIS focalizadas, TypeScript, build y `git diff --check`.
  Separar evidencia simulada de cualquier certificación live posterior autorizada.

No declarar la implementación certificada hasta aprobar todas las pruebas
requeridas. La aprobación documental no acredita código implementado, proveedor
operativo, permisos aprovisionados, ejecución live ni deployment.
