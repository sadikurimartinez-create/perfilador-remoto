# P8.3-H — Aprovisionamiento administrativo de ceipol_app

Estado: procedimiento preparado; no ejecutado live. Requiere autorización administrativa
para el destino acreditado. No contiene credenciales ni modifica DATABASE_URL.

## Propósito y gobierno

ceipol_app es el login runtime de la aplicación. Mantiene LOGIN, NOSUPERUSER,
NOCREATEDB, NOCREATEROLE, NOREPLICATION y NOBYPASSRLS; no debe poseer objetos,
tener memberships ni CREATE efectivo en la base o en public. Sólo se concede
USAGE en public. No hay SELECT global ni grants de tablas/secuencias en UP.

Este contrato acompaña ADR-016 y el hardening de autenticación: la identidad
institucional y sus grants se resuelven en PostgreSQL, sin convertir el runtime
en administrador. P8.3-G (`P8.3-G-INSTITUTIONAL-PROJECT-ACCESS-MIGRATION.md`) y
`institutional-project-access/001_project_access_up.sql` gobiernan por separado
SELECT sobre institutional_project_access. Las demás tablas requieren migraciones
explícitas revisadas. No derivar permisos de roles Cloud SQL ni de Firestore.

## Orden administrativo obligatorio

1. Acreditar servidor, instancia, base y entorno con evidencia sanitizada. No
   imprimir DATABASE_URL, contraseñas ni conexiones con secretos. Usar una identidad
   administrativa aprobada distinta de ceipol_app, también en session_user.
2. Ejecutar `001_ceipol_app_verify.sql` como precheck. Sólo contiene SELECT de
   catálogo. Registrar ausencia del rol o revisar atributos, owners, memberships,
   privilegios efectivos y dependencias existentes. No interpretar cero filas
   de una sección como aprobación global.
3. Ejecutar `001_ceipol_app_up.sql` con parada ante errores y transacción explícita.
   Si existe un rol incompatible, detenerse: no normalizarlo silenciosamente.
   El administrador debe disponer de capacidad autorizada de administración de
   roles y de los permisos necesarios sobre la base y el esquema.
4. Ejecutar VERIFY post: rol existente, canlogin true; super/createdb/createrole/
   replication/bypassrls false; USAGE public true; CREATE public/database false;
   ownership false; sin memberships, writes ni defaults amplios no gobernados.
   Revisar funciones SECURITY DEFINER ejecutables y ACL de PUBLIC. La salida es
   evidencia para revisión humana, no un PASS automático.
5. Aplicar después las migraciones de tablas y grants específicos aprobados,
   incluyendo P8.3-G; verificar cada una con su propio contrato.

UP no establece contraseña. El operador aprovisionará autenticación mediante
el mecanismo institucional aprobado, fuera de estos archivos, sin registrar
secretos en repositorio, chat o consola. LOGIN sin credencial no acredita conexión.

## Límites y fallos cerrados

REVOKE directo no anula CREATE heredado de PUBLIC. Si public o la base permiten
CREATE efectivo, UP aborta y revierte todos sus cambios. La remediación de PUBLIC
es una actuación independiente; este procedimiento no altera permisos de otros
usuarios ni owners. También aborta ante escrituras efectivas de tablas/columnas,
uso mutable de secuencias o defaults amplios. Los SELECT explícitos existentes
requieren inventario y justificación por migración: los catálogos no prueban
su origen. Revisar además funciones con efectos, permisos externos y otras bases;
esta inspección no certifica cuerpos de funciones ni acceso global del clúster.

No usar ceipol_app para ingesta SCINCE, DDL, migraciones, administración, creación
de usuarios ni emisión de grants. La ingesta requiere identidad administrativa
separada y aprobación del procedimiento correspondiente.

## Rollback independiente

Ejecutar DOWN sólo con autorización humana específica y tras desconectar el
runtime por procedimiento separado. Se niega ante owners, memberships, settings,
privilegios o dependencias, incluidas otras bases. Únicamente puede revocar el
USAGE no delegable en public introducido por UP; cualquier resto bloquea DROP.
No usa CASCADE, DROP OWNED, REASSIGN OWNED ni modifica roles terceros. PostgreSQL
mantiene la comprobación final de dependencias; cualquier error aborta la transacción.
Repetir VERIFY para confirmar ausencia sólo después de un rollback aprobado.

No ejecutar live desde el prompt que genera estos archivos. No modificar Vercel,
Cloud SQL, DATABASE_URL ni roles reales durante su preparación.
