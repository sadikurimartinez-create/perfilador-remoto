## INTRODUCCIÓN Y OBJETIVO DEL PLAN DE PRUEBAS

Este documento establece el **Plan Formal de Pruebas de Falla y Resiliencia Distribuida** para la especificación arquitectónica **ADR-019.19 (Transactional Integrity & Event Consistency)**. El objetivo es definir rigurosamente los escenarios de inyección de fallos para validar que el sistema garantiza:
1. No pérdida de evidencia.
2. No pérdida de eventos.
3. No duplicidad.
4. Recuperación ante fallos.
5. Idempotencia.

---

## 1. TEST FIRESTORE FAILURE (Fallo del Event Ledger posterior a Persistencia)

### Escenario de Inyección de Falla
* **Operación:** Ejecución de `saveTemporalComparison` o convalidación humana.
* **Falla Simulada:** Escritura principal en Firestore exitosa, seguida de excepción de red (`Firestore Timeout`) al escribir en `geoint_event_logs`.

### Criterios de Validación:
* **Estado esperado:** Evidencia persistida en Firestore.
* **Outbox:** Entrada generada automáticamente en `geoint_event_outbox` con estado `PENDING`.
* **Retry:** El worker de reintentos (`GeointOutboxDispatcher`) procesa la entrada y emite el evento a `geoint_event_logs`.
* **Reconstrucción:** `rebuildGeointTimeline` reconstruye cronológicamente el evento exitosamente.

---

## 2. TEST DUPLICATE SUBMISSION (Envíos Múltiples y Concurrencia)

### Escenario de Inyección de Falla
* **Operación:** Doble clic rápido sobre `Approve`, `Sweep` o `Generate Report`.
* **Falla Simulada:** Retransmisión concurrente de peticiones idénticas.

### Criterios de Validación:
* **Fingerprint:** Cálculo determinista SHA-256 basado en `(expedienteId, traceabilityId, eventType, entityId)`.
* **Evento único:** `geoint_event_logs` y `geoint_event_outbox` albergan un único registro.
* **Respuesta idempotente:** Retorno de éxito idempotente (`200 OK - Already Processed`) sin duplicar efectos.


---

## 3. TEST PARTIAL TRANSACTION FAILURE (Falla Parcial Transaccional)

### Escenario de Inyección de Falla
* **Operación:** Persistencia transaccional multi-documento.
* **Falla Simulada:** Error forzado entre la escritura del documento principal y el espejo/outbox.

### Criterios de Validación:
* **Rollback:** Aborte inmediato de toda la operación atómica mediante `runTransaction`.
* **Consistencia:** Ausencia total de datos huérfanos en Firestore.

---

## 4. TEST NETWORK INTERRUPTION (Interrupciones y Ciclos de Vida del Cliente)

### Escenario de Inyección de Falla
* **Operación:** Solicitud API con timeout, refrescar navegador (F5) o cierre abrupto de pestaña.

### Criterios de Validación:
* **Recuperación:** Despacho asíncrono outbox en servidor y sincronización íntegra al reconectar.

---

## 5. TEST REPORT CONSUMPTION (Consumo Múltiple de Reportes)

### Escenario de Inyección de Falla
* **Operación:** Generación doble del mismo informe mediante `exportToWord`.

### Criterios de Validación:
* **REPORT_CONSUMED único:** Un único evento en el Ledger para la misma versión y hallazgos.
